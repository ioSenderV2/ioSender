The calls the server must support. Design document, 2026‑08‑08.
Companion Command-Surface-Catalog.md enumerates what the client does to the machine today (~235 write sites / 40 files). This document decides how those cross a wire.
Status Design, not built. DECIDED is settled · OPEN needs a call before implementation · TRAP is a known way to get this wrong.
Branch pr/portable-core — step 6a of the client/server split.

0. Where this sits

The destination is a self‑contained .NET 8 server process with no WPF anywhere — that is step 6b and the v3.0 gate. CNC.Core is already WPF‑free and has run headless on .NET 8 against the real controller, so the destination is not speculative.

What the web pivot (2026‑08‑08) added is an interim: during 6a the endpoint is hosted inside ioSender.exe, which already constructs MachineStateStream and MachineCommandChannel in‑process in MainWindow. That is scaffolding, not architecture. It buys one thing, and it is worth a lot: the web client can be developed and checked beside a known‑good client rendering the same machine live, so when the two disagree the reference implementation is not the variable. It is the machine‑mirror‑window trick scaled to a whole UI, and it is available exactly once — only while both clients exist.

What is missing either way is a transport endpoint and the rest of the surface: today the wire carries machine state one way and jog / run‑control / MDI / realtime the other, perhaps 15% of what a usable client needs. Nothing in the API depends on which process is listening, which is what makes the 6a→6b move a hosting change rather than a redesign.

Decided TypeScript + three.js, served as static files by the host. No client install on any platform. Contract types are generated from CNC.Contracts.dll rather than hand‑mirrored (§1.2).

1. Transport and framing

Decided WebSocket, two connections — JSON text frames for control, binary frames for bulk geometry.
The 6a arrangement. The WPF UI becomes a peer client of the same in‑process channels — both clients render one machine, which is what makes disagreement between them a visible protocol bug. At 6b the host box becomes a headless .NET 8 process and the dashed WPF box disappears; nothing else in the diagram changes.

Why two connections rather than two logical channels on one

TCP is ordered, so on a single socket a Feed Hold sits behind whatever is already in flight — a geometry burst, a delta storm, a program upload. That is head‑of‑line blocking, and it is a bug this project already shipped once: comms replies at Normal(9) outranked operator input at Input(5), so a dense job dispatched no Feed Hold for its entire duration (fixed bbd5207). A dedicated socket with TCP_NODELAY has nothing ahead of it to block on.

Trap The socket is the easy half. A second listener that then posts onto the same server work queue buys nothing — it moves starvation from the wire to the server. The realtime handler needs its own thread writing straight to Comms.com.WriteByte, never through the job pipeline. That is already how MachineRealtimeChannel behaves in‑process; the transport must not undo it. The lesson from bbd5207 was that the transport was never the bug — the marshal was.

Hosting on net462: HttpListener with AcceptWebSocketAsync — the same approach tools/websocket-probe already proves in this repo against the real WebsocketStream. No Kestrel, no sidecar, no new runtime dependency in the WPF host. When the net8 server process eventually takes over (the 6b / v3.0 gate), the endpoint contract is unchanged.

1.1  MachineField crosses the wire as names, not bits

Decided Serialize MachineDelta.Changed as a string array — ["Position","FeedRate"] — with "All" as the snapshot sentinel.

This one is forced, not stylistic. Changed is a 64‑bit flags enum and MachineMirror tests it bitwise about 34 times per delta. JavaScript’s bitwise operators coerce their operands to 32‑bit signed integers, and the contract is already past that line: IsMPGActive is bit 32, IsMetric is bit 33. In a browser changed & 8589934592 evaluates to 0 unconditionally, so a naive TypeScript mirror would silently never apply those fields — and IsMetric is what tells the client whether every coordinate on the snapshot is millimetres or inches.

Names retire the bit budget entirely (the contract has a great deal of growing left to do), remove bit arithmetic from every client, make -debuglog=delta wire logs readable, and give forward compatibility for free — an older client ignoring a name it does not recognise is exactly what the contract already demands of unflagged fields. C# keeps the enum internally; only the serialized form changes, through a name↔flag map at the boundary. The cost is roughly 60–80 bytes per delta instead of 8, at 5–10 Hz.

1.2  Three smaller things settled while here

ItemDecision
IncludeFields DECIDED Required true on every wire serializer, warned in MachineEnums.cs on the GrblState struct itself. A fields‑only struct otherwise serializes as {} — this already shipped once and was caught only by a live wire log (93ce632), because the harness compared through the same serializer.
Position naming DECIDED Rename Position → WorkPosition, and the current WorkPosition → WorkPositionReported or drop it. Today WorkPosition is populated only when the controller reports WPos, which an MPos‑reporting machine — the default, and this one — never does, so it is null forever, while the derived Position is what “where am I in work coordinates” actually means. This caught the C# mirror window (fc1333e8); a remote client author will hit it too. Fix before 6b freezes the wire.
TS types DECIDED Generated from CNC.Contracts.dll by a small net8 reflection tool (tools/tsgen, same pattern as tools/delta-probe), wired as a pre‑build step rather than a chore someone remembers to run. It must carry XML doc comments through as TSDoc — the semantics are the part that bites, and they already live as comments in StateMessages.cs.

2.1  Capabilities (GrblInfo)

About 55 values parsed from the $I handshake: IsGrblHAL, Firmware/Version/Build, AxisFlags, MaxTravel, TravelResolution, NumTools, NumFans, HasATC, HasSDCard, HasFS, HasYModem, HasPIDLog, HasRTC, HomingEnabled, HomingDirection, OptionalSignals, SerialBufferSize, PlanBufferSize, LatheMode, ExpressionsSupported, RotationSupported, plus the Axes and Probes collections.

This is a capability document: it decides which UI exists at all. No SD‑card view without HasSDCard, no tool table without NumTools (this machine reports N_TOOLS 0), and axis count and letters drive every DRO and jog control. It is effectively immutable per connection, so it is a snapshot sent on connect and re‑sent on reconnect or firmware change — there is already a FirmwareChangedHook to hang that on.

Trap GrblInfo is a static class. Crossing the wire needs a MachineCapabilities contract DTO populated from it — not a move. Nothing in Core should stop reading GrblInfo, and the no‑static‑in‑contracts rule stands.

2.2  Settings

Two distinct things, and the client needs both: the values ($n=v, a few hundred of them) and the descriptors — name, group, unit, datatype, min/max, enum members — that GrblConfigControl builds its editor from. grblHAL reports descriptors itself when HasSettingDescriptions; legacy Grbl needs the bundled table. Send descriptors once alongside capabilities, values as a map plus per‑setting change events.

2.3  Console / reply stream

Every controller reply as the console tab shows it, plus the sender’s own annotations. This is not decoration — it is how an operator diagnoses a machine, and how we will diagnose the web client. Source is OnResponseReceived / ResponseLog, and it must honour the existing Silent and ResponseLogVerbose flags.

Trap Coalesce it. The same content at the same rate already killed the WPF UI once: binding whole console content through a join‑all converter on a mutating collection re‑joined 2000 lines per response line and left the UI echoing for minutes after the wire went quiet (fixed 3c97839 with a dirty flag and a 250 ms timer). Batch on a timer, cap scrollback server‑side, and never send one frame per line during a dense stream.

2.4  Geometry — the viewer feed

This is the piece that most shapes the transport, and the good news is that the work is already done server‑side. Renderer.Render(List<GCodeToken>) runs GCodeEmulator.Execute(tokens) and produces exactly five vertex collections: CutLines, RapidLines, RetractLines, ToolOrigin, and ExecutedLines (the progress overlay). The emulator is portable Core and already proven headless on .NET 8.

Decided The client never parses g‑code. The server emulates — where the parser, arc interpolation, WCS rotation and height map already live and are hardware‑proven — and the wire carries packed Float32Array vertex buffers, which is exactly what a three.js BufferGeometry consumes with zero transformation.

Sizing drives the rest. A 220k‑line program at one segment per line is roughly 5 MB of XYZ float pairs, and arcs expand to many segments each, so it can be considerably more. Consequences:

  • Binary frames, not JSON. Base64 inside JSON would inflate about 33% and cost a parse on the largest payload in the system.
  • Chunked, with progress, so the viewer draws incrementally and the UI is never blocked.
  • ExecutedLines is not a buffer — it is an index into the cut buffer. Send “executed to vertex N” on the progress stream and let the client re‑colour by draw range. Re‑sending geometry per progress tick would be absurd.
  • Program load is a server‑side operation with client‑visible progress. It is not instantaneous: a 220k‑line load took 32 s before the OnPropertyChanged marshalling fix brought it to 2.6 s.

3. Client → server: the call surface

3.1  Realtime channel — mostly built

RealtimeCommand already covers 45 of the catalogued sites 1:1. Missing members, from catalog §B (18 sites): Stop (0x19 — the grblHAL realtime Stop, not StopJob), ProbeConnectedToggle (0xA4), Fan0Toggle (0x8A), PidReport (0xA2).

StatusReport / StatusReportAll (0x80/0x87, 10 sites) should not become realtime members. Every one of those sites means “give me a fresh snapshot now”, which is RequestSnapshot() on the state stream — already in the contract, and semantically the right door.

Trap Realtime bytes disguised as text. SpindleControl.xaml.cs:136 and CoolantControl.xaml.cs:56/58/60 send single control characters as strings (GrblCommand.Flood/.Mist are control chars, not g‑code). They must route to the realtime channel. A naive “ExecuteCommand → Mdi” sweep would quietly put the coolant button behind head‑of‑line blocking.

4. The blocking decision: accepted vs completed

The catalog names this as what blocks the offset, settings and probe groups. Having now read all four ack‑wait helpers, here is what is actually in the code.

What exists — four implementations of one idea, none of them agreeing

Every one is new Thread(() => WaitFor.AckResponse(...)) plus while (res == null) EventUtils.DoEvents():

Three findings worth stating plainly:

  1. Grbl.WaitForIdle has no overall cap. It loops SingleEvent(5000) until the state reads Idle, forever. ProbingViewModel’s equivalent grew a 120 s cap and an Alarm check; the Core one never did. Same family as the untimed Comms.AwaitAck that AtcMacros had to wrap by hand.
  2. They do not agree on what “done” means — ok received, versus a status report showing Idle. Those differ by the entire duration of a move.
  3. Every one blocks by pumping the message loop. This is the landmine already flagged for 6b: around 70 DoEvents sites, with connect, settings‑read and macro handshakes all built as synchronous‑reply designs. Over a wire they cannot stay that way.

Proposed design — three named completion levels, and the server does the waiting

Proposed The client does not wait for the machine. The server does, because it is next to the machine and already knows how. The client gets a promise.
Queued        server accepted it; the engine's own gate passed     (immediate)
Acknowledged  controller replied ok / error:N                      (what 4 of the 6 mean)
Idle          everything acked AND machine back to Idle            (what the other 2 mean)

The command envelope carries an id and the desired await level. The server replies CommandAccepted{id} or CommandRejected{id, reason} immediately, then CommandCompleted{id, outcome, replyText, elapsedMs} when the level is reached. The TypeScript client wraps that as a promise resolving at the requested level; the two‑stage form is available for UI — grey the button on accept, spinner until complete — without being mandatory.

Reuse, do not reinvent For the Idle level, StreamPump’s (WAITIDLE) dispatch barrier is exactly this predicate — everything outstanding acked plus two consecutive <Idle| reports — it is event‑driven rather than DoEvents‑spinning, and it is hardware‑verified (2026‑08‑08: wire silent 10,250 ms through real Z moves, tail out 1 ms after clear, zero alarms). Two consecutive reports matter: one is not enough, because a report can be sampled before a queued move has started.

Several things fall out of this that are worth having regardless of the web client:

  • Every wait becomes bounded, including Idle — take ProbingViewModel’s 120 s, not Core’s ∞. That is a real bug fix.
  • Reply text is always carried. SetSetting’s need generalizes; resolve error:N to its message server‑side via GrblErrors.GetMessage so every client gets it for free.
  • Cancellation is a CancelCommand{id} on the main channel — probing already needs it and is the only helper that has it today.
  • Alarm terminates any wait, as ProbingViewModel.WaitForIdle does and the others do not.
  • Server‑side the four helpers collapse into one MachineCommandAck in Core, with the existing WPF call sites becoming its callers. One implementation shared by both clients — not a fifth.
Trap An Alarm:N is not an error:N. An ack wait therefore times out on an alarm instead of failing fast — which is how a validate run once sat there burning its full timeout. The unified helper must watch the state stream for Alarm, not just the reply text.
Open — needs your call Do the WPF client’s ~50 existing ack‑wait call sites migrate onto the unified helper as part of this work, or stay as they are until the web client needs each path? Migrating is more churn now, and strictly better afterwards — one implementation, proven by the client that already runs on real iron.

5. Multi‑client authority

Decided — user, 2026‑08‑09 One writer, unlimited read‑only viewers. Exactly one session holds an operator lease; every other session receives every stream in full but has its commands refused. Full protocol specification in Web-Client-API-Reference.html §5.1.

This was forced by the verification setup — during 6a the web client attaches to an endpoint hosted in the running WPF app, so two clients can reach one machine from day one — but it is the right answer for the target architecture too, where the host is the headless .NET 8 server and a shop could easily have a wall panel, a laptop and a phone all pointed at the same machine. State goes to everyone; a viewer is always safe. Commands were the question, and last‑writer‑wins would mean two people jogging the same axis from different rooms.

Three consequences worth carrying into implementation:

  • No session is privileged. The lease is a protocol object, not a property of being the WPF client. Any rule that only makes sense while WPF exists is a design mistake, since WPF is scaffolding.
  • The stopping set needs no lease. feedHold, stop, softReset, jogCancel and spindleStop are open to every session including viewers. “I could not hit feed hold because I am not the operator” is the wrong failure — and it is also what resolves the hole in a single‑writer design: if the holder’s browser dies at 60% through a program, any viewer can still halt the machine. Viewers may stop, not adjust.
  • The WPF client must be able to go genuinely read‑only during 6a. That is real work in a UI never designed for it, it is throwaway work, and it should be budgeted rather than assumed. It first bites at build step 3 — steps 1–2 have the web client read‑only by construction.

6. Safety items that are new because it is a network

  1. Continuous jog must be dead‑man’d. Today cancel‑on‑release is a local key‑up delivering 0x85 in microseconds. Over a network the release packet can be lost or delayed — and the failure mode is an axis that does not stop. Design: JogStart begins motion, the client heartbeats while the key is held, and the server issues JogCancel the moment a heartbeat is missed. Never rely on the release message arriving. This is the single most safety‑critical piece of the web client.

    Related and already known: a $J= cancelled 3 ms later gets flushed by grblHAL with no reply, which wedged jogging entirely until restart (fix 3eb08c6). Network jitter makes that timing common rather than rare.

  2. Client‑vanish watchdog. The realtime handler serves “operator pressed hold” and “client disappeared” through one code path.

    Open — needs your call Does a vanished client during a running job trigger Feed Hold, or only during a jog? Holding a paying job because a laptop went to sleep is its own kind of harm.

  3. A dead socket has no symptom. Socket.Connected reflects the last I/O, not live state, so writes “succeed” forever into a half‑open link — this project went 5240 polls into a dead link once. The client must detect staleness itself. The Seq‑gap rule already does this for state; the same discipline (count what you sent against what came back over the same window) applies to commands.

  4. Never gate a Feed Hold button on the main channel’s health, or on a command round trip. Show “held” when the controller’s status report says Hold. The realtime channel is fire‑and‑forget precisely so this stays true.

  5. Silence is not death. grblHAL goes completely silent for the duration of a homing cycle, and a naive link‑watchdog aborted a real one because of it. Any liveness check the web layer adds must know that — the existing LinkMonitor lesson applies unchanged one layer up.

  6. DECIDED Bind to loopback until auth exists. Auth becomes mandatory the moment this leaves the loopback interface (6c), not before.
