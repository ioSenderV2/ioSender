## What 3.0 is, and why you might want it

ioSender 3.0 is the first release of this project under its own name. It began as a fork of Terje
Io's ioSender — which is where all the credit for the original belongs — and over the last six months
it has become a different product with different goals. This release carries 207 changes — 65 new
features, 101 fixes and 41 revisions — everything merged since 2.41.

If you are running 2.x today and wondering whether to move, there are four reasons, in the order they
are likely to matter to you.

### 1. This one is being actively developed

That is the headline, and it is a statement about the future rather than about any single feature.

Terje's ioSender is a mature, finished product in light maintenance. That is not a criticism — it is
a reasonable place for a seven-year-old tool to be, it still works, and thousands of people use it
happily. But it is worth being plain about the cadence, because it is what the choice actually turns
on: upstream has shipped **one release in each of the last three years**, and its issue list has
grown to over a hundred open items whose median age is approaching three years. It is stable the way
a finished thing is stable.

This project is in the opposite phase. The 207 changes in this release were written in six months.
Bugs reported get fixed in days, often the same day, because the person fixing them is running the
same machine you are. The codebase is **51% larger** than the one 2.41 shipped from — 154,000 lines
against 102,000.

The trade is real and you should know it before you click install: **active development means a
faster-moving target.** If what you want above all is a tool that behaves identically in two years'
time, 2.x is the safer answer. If you want the bugs you hit to get fixed, this is.

### 2. Significant changes are coming, and the groundwork is already in

The long-term goal is for ioSender to stop being a Windows program.

It is the most-asked-for thing that has never happened. Upstream's issue list still holds five
separate open requests for it — Linux support, a decoupled UI, a MAUI port, a Blazor port, running
under a Windows VM on Linux — and the oldest of them has been open for more than six years.

Today it still is a Windows program — the application is WPF, and WPF is Windows-only. But the work to separate the
machine from the user interface is not a plan, it is in this release. The engine, the g-code
contracts, the shared helpers, the client layer and the SVG-to-laser path **now build as plain .NET 8
libraries with no Windows UI in them at all** — five libraries, compiling clean. One of them already
runs on a Raspberry Pi as an engraving appliance.

What that buys, over the releases after this one: a sender whose brains run as a service with the
screen as a separate thing talking to it. Which means a browser as the screen, a tablet at the
machine, a Linux or Mac desktop, a small box bolted to the enclosure. None of that is in 3.0 and none
of it is promised by a date — but it is the direction, and 3.0 is the release where the foundation
stopped being theoretical.

### 3. It is a far more approachable machine to drive

The original ioSender hands you a capable control panel and leaves the workflow to you. This one has
an opinion about the workflow, and it is built around three tabs you move through in order.

**Work Order** is where a job comes from. You describe the stock and lay out what you want on it —
pockets, contours, holes, text engraved with a V-bit or carved from any installed font, imported SVG
artwork, surfacing, marking, dogboned corners so square parts actually drop in. Each toolpath names
its own tool and operations. Press Generate and you get a g-code program, plus a dimensioned drawing
of the job you can print and work from.

**Setup** is where that job meets the real machine. Probe the corner of the stock, set the work
origin, take a tool-length reference off the toolsetter, probe a height map if the board is not flat.
Everything it measures is checked against the machine's actual travel before anything moves, and it
refuses rather than guesses.

**Job** is where it runs — the program on screen, the 3D view beside it, the run controls in a strip
built for the purpose.

The whole flow is organised around **semi-automatic tool changing**. A program with tool changes in
it is a first-class thing here rather than an interruption: the tool-length reference sequence lives
as a macro on the controller, the program list groups itself into collapsible toolpaths at every M6
so you can run one tool's work on its own or restart from any tool onward, and a tool change no
longer disturbs the work origin the way it used to. If you have a toolsetter and more than one
cutter, this is the part of the product that was designed for you.

### 4. An empty bug backlog, and a number of important fixes in it

Of the 17 issues ever filed against this project, 15 are closed. **Two are open** — both crash
reports, the newer one four days old. There is no queue of known problems waiting for someone to get
to them, because they get fixed as they arrive.

A hundred and one of the 207 changes in this release are fixes. These are the ones worth knowing about,
described by what you would have seen:

**Things that could have damaged the machine or the work**

- A job was run that was bigger than the machine. It drove 200 mm past the end of X and sat grinding
  against the stop.
- Machine Setup showed a wrecked configuration when the controller was perfectly fine — and Apply was
  one press from writing a zero travel limit with soft limits switched on.
- A line the sender could not parse was silently dropped, so the controller ran a different program
  from the one on your screen.
- A connect could finish having read none of the controller's settings and say nothing about it,
  leaving the travel limits, the soft-limit checks and the jog clamp all quietly switched off.
- A probe could false-trigger and report a perfectly successful measurement tens of millimetres away
  from the real surface.
- A probe cycle that failed left the tool standing on the plate.
- Stopping a dry run left an offset behind on the controller that shifted work Z on every job
  afterwards, and survived resets.
- A rotated work coordinate system was stored with the wrong sign and the wrong pivot, so jobs came
  out rotated the wrong way about the wrong point.
- A tool-length offset was reported as missing at exactly the moments it was present.
- The feeds and speeds chart recommended numbers above what the machine could actually do, so the
  chip load it quoted was not the one the cutter saw.

**Things that hung, crashed, or locked you out**

- Connecting to a controller left in check mode looped forever: capabilities unread, reconnect,
  unread, reconnect.
- A controller that resets when the serial port opens failed to connect every single time, with
  nothing actually wrong.
- Feed Hold and Stop could queue behind ordinary traffic instead of taking effect.
- Forty different waits for the controller could spin forever. The app stayed responsive and ignored
  you completely, which is the worst way for it to fail.
- A jog cancelled before the controller saw it left jogging dead until you restarted.
- Loading any program containing G92 while disconnected took the whole app down, and so did every
  generated laser job.
- An error dialog could leave the app beeping at every click with Task Manager the only way to close
  it.
- A crash on startup could leave a half-live process that blocked every later launch.

**Things that were just slow**

- A 220,000-line program took 32 seconds to load, and froze the app while it did. It is now under 3.
- V-carving a script font took minutes. It takes seconds.

## Upgrading from 2.41

- **Your screen layout is kept.** A new installation starts on the ioSenderClassic preset, which is
  the familiar arrangement; an upgrade keeps whatever you already have. A Layout selector in the menu
  row switches between named arrangements if you want to try the new one.
- **Set your spoilboard extent in Machine Setup.** It used to be derived from the machine's travel
  limits, which is not the same thing. Surfacing and the board-extent checks read it from Machine
  Setup now, and say plainly when nothing has declared one.
- **Existing fixtures are converted as they load.** Test position writes the corner it probed straight
  into the fixture, replacing the reference you jogged to by eye.
- **Sounds are off by default.** Settings → User Interface → Sound can attach one to a limit switch,
  the probe, or the machine going into alarm.
- **Loading an SVG as a laser job is off by default**, enabled per launch with **-enableSVGLaserJob**.
- **If you run firmware built from late October 2026 onward, you want this release.** That firmware
  derives its version from a git tag, which dropped the build date out of its version report. Ten
  date-gated feature tests in 2.41 read that as zero, and two of them switched a legacy bug workaround
  **on**. 3.0 is the release that fixes it.
- **Still Windows-only.** The portability work described above is in the libraries, not yet in the
  application.
