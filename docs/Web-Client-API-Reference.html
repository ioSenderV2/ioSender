1. The shape of the API — three tiers and the rule

The API is not purely generic and not purely typed. It is three tiers, and which tier a thing belongs to follows one rule rather than taste.

The membership rule

A capability gets its own typed command when the server knows or does something the client cannot safely reproduce. In practice that is one of four things:

  1. The server owns machine state the client lacks — jog clamping against MaxTravel, soft‑limit handling, ForceSetOrigin, axis letters, lathe mapping. All of this lives in JogController and none of it should be re‑implemented over a network.
  2. Ordering is a safety property — Safe‑Z retract before a lateral move; the fast / retract / slow phases of a probe. As separate lines a client can interleave something between them.
  3. Completion means something specific — a probe is done when the machine is Idle, a setting write is done when its reply text has been read. See await levels.
  4. It is not g‑code at all — realtime bytes, run control, filesystem operations.

Everything else goes through the raw door. That door is not a fallback embarrassment — MDI is a real operator feature (the console entry box), macros are arbitrary g‑code, and there will always be a command nobody wrapped.

TierChannelShapeWhat lives here
1 realtime socket a name, no reply Single‑byte controller commands — feed hold, reset, jog cancel, overrides — plus continuous jog. Never queued, never gated on an answer.
2 main socket op + typed arg + result Anything meeting the rule above: jog step, run control, homing, offsets, probing, settings, filesystem, queries.
3 main socket mdi + one string One line of g‑code or one $ system command, exactly as typed. The escape hatch.
Trap — do not collapse tier 1 into tier 3 Several controls in the WPF client send realtime bytes as text today: SpindleControl.xaml.cs:136 and CoolantControl.xaml.cs:56/58/60 pass GrblCommand.Flood/.Mist, which are single control characters, into a string path. A sweep that maps every ExecuteCommand to mdi would quietly put the coolant and spindle‑stop buttons behind head‑of‑line blocking. They belong in tier 1.

2. Connections, handshake, envelopes

2.1 Endpoints

EndpointProtocolPurpose
GET /HTTPThe web client itself — static files served from the host.
GET /api/helloHTTPUnauthenticated probe: server version, protocol version, whether a machine is connected. Lets a client show something useful before opening sockets.
WS /ws/mainWebSocketState, streams, tier‑2 and tier‑3 commands. JSON text frames plus binary frames for geometry.
WS /ws/realtimeWebSocketTier‑1 only. Separate socket on purpose — see the box below.
Why two sockets TCP is ordered, so on one socket a feed hold queues behind whatever is already in flight — a geometry burst, a delta storm, a program upload. A dedicated socket with TCP_NODELAY has nothing ahead of it. The server side must match: its own thread, writing straight to the controller’s realtime path, never through the job queue. A second socket that then posts onto the same work queue buys nothing.

2.2 Handshake

On /ws/main the server speaks first, unprompted, and in this order:

<- { "type":"hello",        "protocol":1, "server":"2.42.0", "sessionId":"a1b2", "role":"observer" }
<- { "type":"capabilities", ... }          // machine capability document, or null if disconnected
<- { "type":"settings",     ... }          // values + descriptors
<- { "type":"state.delta",  "seq":1041, "changed":["All"], "state":{...} }   // full snapshot

A client is fully populated after four messages and needs no initial requests. Reconnect replays the same four. role is "operator" or "observer" — see §5.1.

2.3 Envelopes

Client → server, main socket. Every call has the same envelope:

-> { "id": 42, "op": "setSetting", "await": "reply", "arg": { "id": 110, "value": "5000" } }
FieldTypeMeaning
idnumberClient‑assigned correlation id, unique per connection. Echoed on every reply.
opstringThe command name, from §5.
awaitstringHow complete the client wants it before command.completed is sent. Optional; each command has a sensible default.
argobjectCommand‑specific, documented per command.

The four await levels. This is the part of the API most worth understanding, because the same command means different things at different levels, and because the existing client has four inconsistent implementations of this idea — timeouts from 400 ms to unbounded, two different definitions of “done”. The server owns the waiting; the client just says how much of it it wants.

LevelCompleted whenUse it for
queuedThe server accepted it and the engine’s own gate passed. Immediate.Fire‑and‑forget; UI that derives truth from the state stream anyway.
acknowledgedThe controller replied ok or error:N.Default for most commands. Offsets, unlock, filesystem.
replyAs acknowledged, and the reply text is returned in the result.Settings writes (the error:N message matters), $G/$# queries, diagnostics.
idleEverything outstanding is acked and two consecutive <Idle| status reports have arrived.Motion the client must sequence behind: probe, goto, home, macro call.
Implementation note The idle predicate is not new work. StreamPump’s (WAITIDLE) dispatch barrier is exactly this — everything acked plus two consecutive Idle reports, event‑driven rather than spinning — and it is hardware‑verified. Two reports matter: one can be sampled before a queued move has started. Every level is bounded by a timeout; there is no unbounded wait in this API.

Server → client replies, correlated by id:

<- { "type":"command.accepted",  "id":42 }
<- { "type":"command.completed", "id":42, "outcome":"ok", "reply":"ok", "elapsedMs":31 }

<- { "type":"command.rejected",  "id":43, "code":"notPermitted",
     "message":"This session is an observer." }
<- { "type":"command.completed", "id":44, "outcome":"error", "code":"controllerError",
     "reply":"error:9", "message":"G-code locked out during alarm or jog state", "elapsedMs":12 }

command.accepted always precedes command.completed, so a UI can grey a button immediately and show a spinner until completion. A rejection produces command.rejected alone — nothing was sent to the machine.

3.1 capabilities

A projection of GrblInfo — about 55 values parsed from the $I handshake. This is a capability document: it decides which UI exists at all. No filesystem view without hasFS, no tool table when numTools is 0 (as on this machine), and axisLetters drives every DRO and jog control. Effectively immutable per connection.

{ "type":"capabilities",
  "connected": true,
  "firmware":"grblHAL", "version":"1.1f", "build":20260712, "isGrblHAL":true,
  "identity":"...", "driver":"...", "options":"...",
  "axisLetters":"XYZ", "axisCount":3,
  "maxTravel":  [500.0, 400.0, 120.0],
  "resolution": [0.005, 0.005, 0.005],
  "homingEnabled":true, "homingDirection":["X","Y","Z"],
  "numTools":0, "numFans":1, "hasATC":false, "manualToolChange":true,
  "hasSDCard":false, "hasFS":true, "hasYModem":true, "uploadProtocol":"YM",
  "hasPIDLog":false, "hasRTC":true, "hasVariableSpindle":true, "hasReversableSpindle":true,

Trap GrblInfo is a static class in Core. This message is a DTO populated from it, not a relocation of it. Nothing in Core should stop reading GrblInfo, and no static may enter the contracts assembly.

3.2 settings

Two things the client needs, and it needs both: the values, and the descriptors that make an editor possible. grblHAL reports descriptors itself when it advertises them; legacy Grbl needs the bundled table. Descriptors arrive once; values change individually via settings.changed.

{ "type":"settings",
  "values": { "110":"5000.000", "111":"5000.000", "13":"0", ... },
  "groups": [ { "id":6, "name":"Axis 0" }, ... ],
  "descriptors": [
    { "id":110, "groupId":6, "name":"X-axis maximum rate", "unit":"mm/min",
      "dataType":"FLOAT", "min":0, "max":null, "values":null, "description":"..." },
    { "id":13,  "groupId":3, "name":"Report in inches", "unit":"",
      "dataType":"BOOL", "values":null, "description":"..." }
  ] }

dataType is the string form of GrblSettingDetails.DataTypes: BOOL, BITFIELD, XBITFIELD, RADIOBUTTONS, AXISMASK, INTEGER, FLOAT, TEXT, PASSWORD, IP4. For the mask and enum types, values carries the member names in bit order.

3.3 state.delta BUILT

The existing MachineDelta. seq increases by exactly 1 per message; a gap means the client missed one and must resync via requestSnapshot rather than keep applying. A full snapshot is simply a delta with changed:["All"], so connect, resync and steady state are one code path.

{ "type":"state.delta", "seq":1042,
  "changed":["Position","FeedRate","GrblState"],
  "state": {
    "grblState": { "state":"Run", "substate":0, "lastAlarm":0, "error":0, "mpg":false },
    "position":[10.125, -4.0, 2.5],
    "feedRate":800.0,
    "isMetric":true,
    ...
  } }
FieldNotes
changedAn array of field names, not a bitmask. Fields not listed have unspecified content and must be ignored. ["All"] is a full snapshot.
positionWhere you are in work coordinates — this is the field a DRO shows.
machinePositionMachine coordinates.
null elementsA null in a position array means that axis has no reading (not homed, never reported). NaN never crosses the wire.
Two traps this message has already sprung

Bitmask → names is not cosmetic. JavaScript’s bitwise operators coerce to 32‑bit signed integers and the field set is already at bit 33, so a numeric mask would make isMetric and isMPGActive silently unreadable in a browser — and isMetric is what says whether every coordinate here is millimetres or inches.

position, not workPosition. The old contract also had a workPosition field populated only when the controller reports WPos — which an MPos‑reporting machine, the default and this one, never does. It was null forever and it fooled the C# mirror window. This spec renames the derived value to position and drops the trap.

3.4 console

Every controller reply as the console tab shows it, batched. Not decoration — it is how an operator diagnoses a machine.

{ "type":"console", "lines":[
    { "t":1754706123123, "dir":"tx", "text":"G0 X10" },
    { "t":1754706123140, "dir":"rx", "text":"ok" } ] }
Trap Batch it, cap it, never one frame per line. This exact content at this exact rate already killed the WPF UI once: the console re‑joined 2000 lines per response line and left the UI echoing for minutes after the wire went quiet. Coalesce on a ~250 ms timer and cap scrollback server‑side.

3.6 Geometry — geometry.begin, binary frames, geometry.end

The client never parses g‑code. The server runs the existing GCodeEmulator — where the parser, arc interpolation, WCS rotation and height map already live and are hardware‑proven — and ships the same five vertex collections the WPF renderer builds, as packed little‑endian float32 triples that drop straight into a three.js BufferGeometry.

<- { "type":"geometry.begin", "programId":7,
     "buffers": { "cut":184320, "rapid":2048, "retract":512, "toolOrigin":2 },
     "bounds": { "min":[0,0,-3.2], "max":[120.5,80.0,5.0] } }
<- [binary frame] [binary frame] ...
<- { "type":"geometry.end", "programId":7 }

buffers gives vertex counts up front so the client can preallocate once. Each binary frame is a chunk:

OffsetTypeFieldNotes
0char[4]magic"IOGB"
4uint8version1
5uint8bufferId0 cut · 1 rapid · 2 retract · 3 toolOrigin
6uint16flagsbit 0 = last chunk of this buffer
8uint32programIdDiscard chunks whose id is not the current program — guards a reload mid‑transfer
12uint32vertexOffsetIndex of the first vertex in this chunk
16uint32vertexCount
20float32[]xyz3 × vertexCount, little‑endian

The executed overlay is not a buffer. It is executedToVertex on job.progress — an index into the cut buffer that the client renders as a draw range. Re‑sending geometry per progress tick would be absurd: a 220k‑line program is several megabytes before arc expansion.

3.7 event

{ "type":"event", "kind":"alarm",   "code":1,  "message":"Hard limit triggered..." }
{ "type":"event", "kind":"error",   "code":9,  "message":"G-code locked out during alarm or jog state" }
{ "type":"event", "kind":"message", "text":"Tool change: insert T3" }
{ "type":"event", "kind":"connection", "connected":false, "reason":"link lost" }
Trap An Alarm:N is not an error:N. An alarm does not produce an error: reply, so a naive ack wait times out on one instead of failing fast. Any await level must watch the state stream for Alarm, not only the reply text.

3.8 prompt

A running macro can stop and ask the operator something — the (MBOX ...) and (PROMPT ...) directives. The server sends a prompt and blocks the stream until an answer arrives.

<- { "type":"prompt", "promptId":3, "kind":"mbox", "buttons":"okCancel",
     "text":"Jog to the corner and set zero, then press OK" }
-> { "id":51, "op":"answerPrompt", "arg":{ "promptId":3, "answer":"ok" } }
Trap Cancel is not a soft finish. Prior moves may still be physically executing, so a cancelled prompt routes to the engine’s real abort path. In this codebase that method is Abort(), not Stop() — the naming is inverted, and Stop() means “already stopped, do not send the stop byte”. Wiring cancel to Stop() once let a Z axis run to completion after the operator cancelled.

4. Tier 1 — the realtime socket

Text frames carrying a command name. No id, no reply, no result — by design. The source of truth for “did the hold take” is the machine’s next status report on the state stream, never a round trip here. Gating a feed‑hold button on an answer would recreate the starvation bug this socket exists to avoid.

4.2 Continuous jog — the dead‑man protocol

The most safety-critical part of this API

Locally, cancel‑on‑release is a key‑up delivering 0x85 in microseconds. Over a network the release packet can be delayed or lost, and the failure mode is an axis that does not stop. So release is never the mechanism. The client proves it is still holding the key; the server stops the axis the moment that proof lapses.

-> { "op":"jog.start", "axes":{"X":1,"Y":-1}, "mode":"fast" }
-> { "op":"jog.keepalive" }        // every 100 ms while the key is held
-> { "op":"jog.keepalive" }
-> { "op":"jog.stop" }             // normal release - server sends 0x85 immediately
RuleValue / behaviour
Keepalive interval100 ms, client‑driven
Server deadline250 ms after the last message. On expiry the server issues jogCancel unconditionally.
Socket closeTreated as an immediate deadline expiry. A closed tab stops the axis.
Orderingjog.start renders through the real JogController — clamping, soft limits, ForceSetOrigin, G91/G53, axis letters, lathe mapping. The client never formats $J=.
Known hazard this interacts with A $J= cancelled a few milliseconds after it was issued gets flushed by grblHAL with no reply at all, which once wedged jogging completely until an app restart (fixed by ReleaseFlushedJogMdi). Network jitter makes that timing common rather than rare, so the server‑side jog path must keep that release valve and must purge stale queued jogs rather than replay them.

5. Tier 2 — typed commands

All on /ws/main, all using the envelope. “Default” is the await level used when the client omits one.

5.1 Session

opargDefaultNotes
requestOperator—acknowledgedAsk for the operator lease. OPEN
releaseOperator—queued
requestSnapshot—queuedForce a full state.delta. The Seq‑gap resync path. BUILT
answerPrompt{ promptId, answer }queued§3.8
Open — blocks this section Because the web client attaches to a running WPF app, two clients can command one machine from day one and there is no rule yet. My recommendation is an operator lease: one holder, the WPF host by default, handover explicit and visible in both UIs, everyone else read‑only. The alternative — last writer wins — means two people can jog the same axis from different rooms. This decides whether the envelope needs a lease token, so it wants settling before implementation.

5.2 Motion and position

Trap — homing grblHAL goes completely silent for the whole homing cycle. No status reports, no replies. A liveness check that treats silence as a dead link will abort a real homing run — which has happened here. The idle await on home must tolerate a long quiet period, and any watchdog must know about it.

5.5 Controller filesystem

Present only when hasFS or hasSDCard. All 12 sites are in the SD card view today.

Trap — never list the filesystem mid‑stream A $F or $CWD issued while a job or macro is streaming produced error:9 and killed a run before it wrote its work origin. Guard on the sender’s job state, never on the controller’s GrblState — a macro sitting at a wait looks Idle. The server must refuse these with busy rather than pass them through.

6. Tier 3 — raw MDI

opargDefaultNotes
mdi{ line:"G0 X10 Y10" }acknowledgedBUILT — one line, exactly as typed, through the same parse path the MDI box uses.

One line per call, never a batch: a batch would be a program, and programs go through loadProgram so they get validation, geometry and progress. The server still applies its normal line handling — parse, block counting, response logging — so an MDI line behaves exactly as one typed into the desktop client.

Trap — never stream o‑word flow control o100 if [...] and friends belong only in a .macro file on the controller. Streaming one line‑by‑line wedges the interpreter: MPos freezes, jogging dies, and reverting does not fix it — it needs a soft reset, $X and a re‑home. The server should refuse o‑word lines through mdi rather than pass them along.

7. Refusals, outcomes, error codes

Refusal is not failure. A command.rejected means nothing reached the machine. The gates are the engine’s own enable‑state — the same booleans the WPF run bar’s buttons bind — so a client is refused precisely when the corresponding button would be greyed. There is no second gating implementation to drift out of step.

codeMeaning
notPermittedThis session is an observer, not the operator.
notAvailableThe engine refuses in the current state — nothing to stop, cannot run, not connected.
busyA job or macro is streaming and this command must not interleave (see the filesystem trap).
unsupportedThe connected controller lacks the capability — check capabilities first.
badRequestMalformed argument, unknown op, unknown axis letter.

command.completed carries an outcome instead — the command was sent:

outcomeMeaning
okReached the requested await level cleanly.
errorController replied error:N. reply has the raw text, message the resolved description.
alarmAn alarm ended the wait. code is the alarm number.
timeoutThe await level was not reached in time. Every level is bounded.
cancelledA cancelCommand or a machine reset ended it.

8. Deliberately not in the API

Not exposedWhy
Raw byte write to the controllerTier 1 covers every realtime byte by name. An arbitrary‑byte door would let a client bypass every gate in this document, and no legitimate client needs it.
Streaming a program line‑by‑line from the clientFlow control, buffer accounting, tool changes, probing look‑ahead and the barrier directives all live in the server’s streamer. A client that streams is a second, worse streamer — and would inherit none of the hardware‑verified behaviour.
Choosing which file runProgram runsThe loaded job is server state, shared by every client.
Sender configuration (App.config)Desktop client state — window geometry, themes, editor choice. The web client has its own preferences; it does not edit the desktop client’s.
g‑code parsing or geometry generation client‑sideThe server already does it, correctly, with arcs, WCS rotation and height maps. Two implementations would disagree, and the client’s would be the wrong one.
